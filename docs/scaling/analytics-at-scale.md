# Analytics at Scale

**Status: proposal.** Select a new data plane only after repeatable measurement shows that the existing pipeline or shared PostgreSQL workload is the limiting factor. Current behavior is in [Analytics and Measurement](../domains/analytics-and-measurement.md); capacity evidence belongs in [Performance and Capacity](../performance/README.md).

| Stage | Design | Good fit | Trade-offs |
|---|---|---|---|
| Current stack, improved | Keep PostgreSQL, Redis, and RabbitMQ; batch consumer inserts; bound buffers; add queue-age and database-wait alerts; precompute dashboard summaries. | First step while volume and query cost remain manageable. | Analytics still shares database resources unless storage or compute is separated. Batching and retry behavior need idempotency and recovery tests. |
| PostgreSQL partitioning and rollups | Time-partition high-volume event tables, query only relevant partitions, and maintain reporting summaries. | Retention and date-filtered reports are the main pressure points, and keeping ordinary PostgreSQL is valuable. | Partition design and maintenance matter; partitioning alone does not remove ingest contention on the same database. PostgreSQL supports declarative partitioning and pruning, and old partitions can be detached or dropped for lifecycle management. [PostgreSQL partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html) |
| Separate PostgreSQL/Timescale analytics database | Send analytics into an independently sized time-series database and serve dashboards from incrementally refreshed aggregates. | The team wants SQL/PostgreSQL workflows and needs to isolate analytics CPU/IO from commerce. | Adds a database, migration/backup/monitoring work, and eventual consistency. Timescale continuous aggregates update summaries incrementally in the background; verify extension and hosting support before choosing it. [Timescale continuous aggregates](https://docs.timescale.com/use-timescale/latest/continuous-aggregates/) |
| Event stream and analytical store | Publish versioned events to Kafka or a compatible managed stream; consume into ClickHouse; build aggregate tables/materialized views for dashboards. | Sustained high event volume, replay/reprocessing, multiple independent consumers, or analytics query load that should not touch OLTP. | More infrastructure and operational skill; define partition keys, retention, schema evolution, duplicate handling, backpressure, replay, and freshness guarantees. Kafka stores retained partitioned event streams; ClickHouse documents Kafka ingestion and incremental materialized views that shift repeated aggregation work toward insert time. [Kafka docs](https://kafka.apache.org/documentation/), [ClickHouse Kafka integration](https://clickhouse.com/docs/integrations/kafka/kafka-table-engine), [ClickHouse incremental materialized views](https://clickhouse.com/docs/materialized-view/incremental-materialized-view) |

Flink is an optional stream processor when the product requires stateful event-time windows, joins, late-event handling, or complex streaming transformations. It should not be added just to move rows from a broker into an analytical database. [Apache Flink concepts](https://nightlies.apache.org/flink/flink-docs-stable/docs/concepts/overview/)

The staged recommendation is: measure first; batch and bound the current pipeline; isolate analytics storage if shared-database contention is confirmed; adopt a partitioned event stream plus analytical store when replay, consumer fan-out, or sustained event volume makes that operational cost worthwhile. Keep payments, inventory, orders, and wallet ledger truth in PostgreSQL.

## Dashboard freshness and delivery

The current web dashboards poll cached summaries every 30 seconds and detail endpoints every 60 seconds; server results have a 20-second cache window. If product requirements call for fresher results, first serve incrementally maintained aggregates from an analytics store so refreshes do not repeatedly scan raw commerce tables. Then compare polling of compact aggregate snapshots with a one-way SSE stream that announces aggregate versions or carries small updates. SSE fits server-to-browser updates; WebSockets add bidirectional connection management that the dashboard does not currently need. A push transport alone does not reduce ingest writes or reporting query cost, and should be introduced only after the aggregate pipeline and freshness target are defined.
